# 타격 버벅임 측정과 최소 수정 — 배포 보류

**입력 순간의 큰 동기식 멈춤은 줄었지만, 기존 버전의 프레임 예산에는 아직 도달하지 않았다. 성능 합격·서비스 배포 완료로 보고하지 않는다.** 승인 포즈·100ms 판정 시점·임팩트 이후 기존 운동학 곡선은 바꾸지 않았다.

## 재현 조건과 비교 범위

- 기준 게임 `db31b7e` / v5.160.25, 수정 전 통합 후보 `465d2b2`, 동일 v5.160.25 업무 코드 위의 성능 수정본 `0f6acf4`를 비교했다. 수정본 원본은 private 저장소의 `benchmark/batting-stutter-v516025`에도 보관했다. Raw after 데이터의 SHA256은 해당 커밋의 index.html과 일치한다.
- 실제 배포용 후보 작업은 이후 최신 Claude v5.162.0 / `de2d44b` 위로 재배치했다. 뉴스·선수 카드·마이너/커뮤니티 등 타 작업을 되돌리지 않았다. 기준 버전 비교 자료와 최신 코드에서 수행한 기능 검사를 구분한다.
- Chromium, 모바일 **390×844** / PC **1280×720**, 같은 서버에서 직렬 실행. CPU AMD EPYC 9V74, 컨테이너 CPU 할당 4코어. 모바일은 화면 크기이며 휴대전화 CPU/GPU 에뮬레이션이 아니다. **실제 iPhone Safari는 미검증**.
- 시드 4242의 실제 LiveGame → detectDecision → showDecision → acpPA에서 준비/스윙 입력을 자동화했다. 실제 RAF/performance.now를 사용했다. UI가 이미 준비된 상황을 비교하기 위해 오프닝과 와인드업 전의 고정 650ms 대기만 동일하게 생략했다. 와인드업·공 비행·스윙·판정 시간은 배속하지 않았다.
- 실제 apPitchPlan에서 생성된 직구의 코스만 검사 좌표로 고정하고 실투를 끈 테스트 fixture다. 판정·타구/수비 결과 함수의 반환값은 조작하지 않았다. 중앙 u=0/w=0, 외곽 u=1/w=0을 분리했다. 각 빌드/화면의 동일 인덱스 50개 투구(type/kmh/T/u/w)는 전부 일치한다.
- **계획한 입력 시점**은 공 도착 100ms 전(타이밍 헛스윙은 650ms 전)으로 동일하다. 메인 스레드 지연 때문에 실제 입력 전달 시각을 억지로 같게 만들지는 않았다. 실제 전달 지연을 따로 보관했다. 물리 시계를 가짜로 고정한 시험이 아니다.
- 정식 주 비교는 3빌드×2화면×50회=300회. 지원/기존 모션 전환 코스 각25회. 이 corpus의 공정 타구는 결과상 HR이었다. 일반 안타를 누락한 것으로 처리하지 않도록 무풍·커서 오프셋 안타 fixture를 각10회 추가했고 모두 실제 3B였다(추가60회). 중간 캐시/중복 그리기 실험200회도 별도 보관: **총560회**, 워밍업·예비 측정 제외. 결과를 강제로 HR/3B로 바꾼 것이 아니다.

## A. 프레임 및 입력 처리 비용

RAF 통계는 측정 구간의 프레임을 모은 값이다. 입력 처리 시간은 act() 호출 전후의 동기식 시간이며, 이벤트 전달 지연과 구분한다. >33.3ms, >50ms는 요청한 엄격한 임계값이다. 33.3/33.4 및 50.0/50.1ms에는 타임스탬프 양자화 영향이 있으므로 count와 정규화 비율을 함께 본다.

| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| mobile / v5.160.25 | 8099 | 16.69 | 33.4 | 16.8 | 16.8 | 9 | 0 | 6.15 |
| mobile / 수정 전 465d2b2 | 6547 | 22.26 | 249.9 | 33.4 | 116.7 | 921 | 189 | 113.32 |
| mobile / 성능 수정 | 6800 | 20.07 | 66.7 | 33.4 | 33.4 | 996 | 11 | 14.16 |
| pc / v5.160.25 | 7994 | 16.95 | 116.6 | 16.8 | 33.3 | 93 | 3 | 6.86 |
| pc / 수정 전 465d2b2 | 6283 | 22.72 | 250.1 | 33.4 | 133.4 | 1006 | 149 | 119.91 |
| pc / 성능 수정 | 6676 | 20.37 | 83.4 | 33.4 | 33.4 | 1040 | 10 | 14.99 |

**최종 RAF P95는 양쪽 모두 33.4ms로 기준 16.8ms보다 높다.** 긴 멈춤의 감소를 60fps 복구나 무버벅임 합격으로 바꿔 말하지 않는다. 입력 처리 비용도 기준보다 높다.

### 발생 위치와 확인한 비용

1. **입력/CONTACT 직전:** 수정 전 paint()에서 코스 안전성 검사 86개 source pose를 동기 계산했다. 같은 입력 핸들러에서 첫 상태 그리기와 첫 스윙 그리기를 연달아 수행했고, 모델 폐기와 부동소수점 투영값 기반 key 때문에 다시 계산하기도 했다. 예비 측정에서 input 92~130ms, 단일 draw 약95~114ms, RAF 최대250ms를 확인했다. 첫 CONTACT 구간 상당 부분이 그 계산 중 지나갈 수 있다.
2. **준비/FINISH 주변:** 수정 전 측정 구간의 factory 호출 수는 모바일206, PC159였다. 수정 후35/36으로 줄었다(초기 로딩 밖의 전체 페이지 모델 수가 아니라 측정 구간 호출 수). 투구 팔로스루와 이른 타자 스윙이 동시에 살아 있는 구간에는 같은 RAF에서 중복 raster가 있었다. 상태 갱신을 그대로 두고 중복 그리기만 합쳤다.
3. **지속적인 렌더링 비용:** 승인 렌더러의 소프트웨어 깊이 검사·Canvas readback이 남아 있다. 최종 지원 코스 actor P95는 대략11ms 수준으로, 필드와 UI/합성 비용을 더하면 16.7ms 예산을 넘는 프레임이 생긴다. 정확한 GC 정지 시간을 따로 분리하지는 못했다. Heap/longtask 표본과 임시 할당 감소 근거는 보관했으며 GC만을 원인으로 단정하지 않는다.
4. **수비 화면 전환:** 지원 코스의 field 전환 구간 P95는 약16.7ms다. 이번 데이터에서 가장 큰 반복 멈춤은 필드 전환 자체보다 입력/모션 렌더링 쪽이었다. 단계별 창 통계는 summary.json의 windows와 summary.csv에 있다. 모든 단발 긴 프레임의 원인을 개별 확정한 것은 아니다.

## 적용한 최소 수정

- 모델 cache를 투영 부동소수점 문자열 대신 코스 입력·외모·실제 레이아웃으로 식별하고 재사용한다. 시작/투구마다 준비된 모델을 버리지 않는다.
- 실제 투구 코스는 와인드업 때 알려 주어 검사를 입력 전에 분산한다. 같은 10ms 격자를 약3ms idle 작업으로 나누고 최초 관절 위반에서 중단한다. 검사에 사용하지 않는 머리 mesh는 geometry-only 경로에서 만들지 않는다. 준비되지 않은 값은 임의의 새 포즈로 그리지 않는다.
- 팔 깊이/owner typed array와 scratch canvas를 재사용한다. 원래와 동일한 각 segment 영역(14SD margin)만 readback/process한다. 깊이 수식·그리기 순서·알파 기준·원래 해상도는 유지한다.
- 같은 입력 핸들러의 보이지 않던 첫 raster를 제거했다. 같은 RAF timestamp의 windup/swing 중복 raster도 합쳤다. windup의 릴리스 조건·구간 키/보간값은 보존했고 RAF timestamp 전달만 추가했다.

17개 렌더링 시점의 readback은 12,871,344→4,572,156 bytes로 **64.48% 감소**했다. 호출 횟수는 양쪽 102회로 동일하다.

## B. 시간 압축에 의한 움직임 변화 — 미수정

PLANT가 완료된 보통 입력에서 source900→1120ms를 실제100ms에 재생한다. 현재 Hermite clock의 시작/끝 배율은1이지만 중간 배율은 **2.8**이다. CONTACT 경계 좌우 미분은 약1.000036/1.000000으로 C1은 유지된다. 그러나 C1은 자연스러운 가속도를 보장하지 않는다. 일찍 눌러 PLANT 전부터 출발한 경우에는 압축량이 더 커질 수 있다.

- 수학적인 정상100ms 창과 기존 source의 골반/어깨 각속도, 양손/배트 헤드 속도를 1ms 간격으로 분리했다. READY~FINISH 실제 그리기 시각/각도 표본도 별도로 그래프화했다.
- 포즈를 그대로 두고 입력 판정100ms도 고정한 상태에서, 원래220ms 동작을 원래 속도 그대로 모두 보여 줄 수는 없다. 다음 검토안은 **판정 시각을 유지한 시간 배분/C2 곡선 비교**다. 속도를 일정하게 만들거나 원래 동작 시간을 바꿔 숨기는 수정은 하지 않았다.
- 최종 속도 그래프는 성능 수정 전후에 동일하다. 관절·그립·배트 각도나 시간 매핑 함수 자체는 이번에 변경하지 않았다.

## C. 임팩트 직후 감속 — 원인 구분, 원본 수정 보류

중앙 reference를 다시 미분하면 source1110ms 약17.96, 1120ms 약17.69, 1130ms 약8.32, 1140ms 약5.73m/s다. 미분 간격/중앙 투영 때문에 이전 17.75와 소수 차이는 있으나 10ms 급감속은 재현된다.

이 움직임은 ContactExtension의 미리 정한 Hermite/관절 제약 경로다. 공/배트 질량·관성·반발계수로 계산한 감속이 아니므로 **정상 충격이라고 확인할 물리적 근거가 없다.** FPS 지연과는 별개로 툭 끊겨 보일 수 있다. 사용자 승인 없이 승인된 EXTENSION을 고치지 않았다. 별도 수정안은 CONTACT endpoint와 승인된 뒤쪽 endpoint를 고정하고 초기30~50ms의 가속도/손 경로를 따로 비교하는 것이다.

## 보존·기능 검사 / 실제 녹화

- 승인된 다섯 원본 파일의 바이트/SHA256 유지. 검사 fast path와 원본 full path의 world 좌표351표본 차이0. 17개 시점 전체 캔버스 픽셀 차이0, 팔 segment coverage/visibility/owner 통계도 동일(preservation.json).
- 최신 Claude 대비 판정/공 물리/기록/리그/저장 함수와 기존 선수 렌더러 본문을 비교했다(isolation.json). windup은 timestamp 전달을 제거해 정규화하면 원래 동작 본문과 같다.
- 현재 코드의 실제 수비 결과→1타석·1안타 증가→저장/로드 유지 확인. 별도 bounds 검사는 코스 검사가 끝난 상태에서 READY~FINISH를 샘플링한다. 입력 준비 시간/성능 검사를 대체하는 자료가 아니다.
- 실제 입력 fixture의 HR·파울·타이밍 헛스윙 및 보충 안타(3B), 지원/기존 모션 전환을 확인했다. 최신 코드의 smoke/compat/prosoak, lint, 로컬 암호화 패키징 결과는 checks.json에 기록한다. 앞서 알려진 growtest 중계 투수 기대값 실패를 이번 범위에서 고쳤거나 통과했다고 보고하지 않는다.
- 영상은 **실시간 Chromium 녹화, 정상 속도**다. 녹화 오버헤드는 위 성능 통계에서 제외했다. 독립 녹화이므로 두 영상의 프레임을 임의로 정렬하거나 보간하지 않았다. 실제 휴대전화 영상도 아니다.

## 재현과 상태

1. 로컬 서버8998을 실행한다. `MODE=baseline|before SIZE=mobile|pc COUNT=50 node gpt-review/batting-performance/measure.cjs`.
2. 같은 업무 코드에서의 수정본 재현은 `MODE=after AFTER_REF=benchmark/batting-stutter-v516025`를 지정한다. `OUTCOME=hit COUNT=10 TAG=after-hit`는 무풍 보충 안타 fixture다. 각 버전의 태그를 다르게 둔다.
3. analyze.py / plots.py는 raw JSON에서 통계/그래프를 다시 만든다. preservation.cjs는 원본 바이트와 실제 픽셀을 비교한다. figures는 표준 matplotlib 산출물이다.

**현재 결론: 큰 동기식 입력 stall은 개선. 잔여 프레임 예산·시간 압축·승인된 임팩트 감속은 해결 완료가 아니다. claude/next 병합 및 GitHub Pages 배포 금지 상태를 유지한다.**
