## 실제 구현과 기존 코드 검토

기존 `index.html`의 `mvSD`, `sdRibbon`, `sdArm`, `sdCel`, `sdPal`을 읽었다. 기존의 연속 리본형 팔다리, 단순 명암, 공유 유니폼 구조는 유용하다. 하지만 기존 오프닝의 표면별 좌표/레이어를 바꿔 결과를 숨기지 않기 위해, 이번에는 기존 함수를 수정하거나 타격용 렌더러를 복제하지 않았다.

새 모듈은 독립된 `(CanvasRenderingContext2D, options)` 입력만 받는다. 전역 게임 상태, 저장, 타격/수비 로직, 승인 렌더러를 호출하지 않는다. 실제 게임과 동일한 브라우저 Canvas 2D API를 쓰지만 **아직 게임에 통합하지 않았다.**

- 좌표: +Y 아래, +Z 가슴, +X 해부학적 왼쪽. 동일 좌표를 yaw로 투영.
- 골반→척추→양 어깨→팔꿈치→손목, 골반→양 고관절→무릎→발목의 연결. 작은 굴곡에서 부모 회전을 자식에 전달한다.
- 몸통은 여러 단면의 흉곽/허리 곡면, 다리는 고관절·무릎·발목을 지나는 연속 튜브다.
- 얼굴/모자/유니폼은 코드 도형과 문자다. 컨셉 이미지는 렌더러에서 불러오지 않는다. 사진·공식 벡터 경로를 복사하지 않았다.
- 얼굴 특징과 옷 표시는 곡면 부착용 레이어, 모자는 머리 위 레이어로 나눈다. 중립 자세용 파츠 단위 painter sorting으로, 전신의 정확한 픽셀 깊이 검사가 아니다. 팔이 가슴을 가로지르는 실제 투구에서 가림이 올바른지는 **미검증**이다.
- Canvas `Path2D`로 같은 색의 면을 묶어 그린다. `getImageData`, 소프트웨어 픽셀 깊이 루프, WebGL, 외부 이미지 렌더링 없음.
- 생성한 경로는 최대12개 자세/시점에 한해 재사용한다. `clearCache()` 및 검증 페이지 `pagehide` 정리.

## 생성 컨셉과 실제 구현의 차이 — 미달 사항

1. 실제 Canvas 얼굴은 더 평면적이고 눈·코·턱 표현이 단순하다. 컨셉과 동등한 외형 품질을 달성했다고 판단하지 않는다.
2. 곡면 명암이 제한된 색면이라 경계가 각지며, 머리/귀/신발의 일부 단면이 도형처럼 읽힌다.
3. 손은 작은 손바닥과 손가락으로 나누었지만 개별 손가락 리깅/그립은 없다.
4. 가슴 문자는 일반 시스템 글꼴로 그린 자리 표시자라 컨셉의 손글씨형 로고와 다르다.
5. 골격 연결은 공통이나 완성된 3D 스키닝이 아니다. 실제 투구의 큰 회전, 팔 가림, 몸통 비틀림, 유니폼 변형은 아직 검증하지 않았다.
6. 생성 시트도 곽빈의 얼굴·체형을 정확히 재현했다는 근거로 사용할 수 없다. 외형 승인 필요.

## 검사 결과와 기술적 결론

브라우저 pageerror 0. 0/38/90도 좌표 유한, 모바일 경계 안에 전체 도형이 들어온다. 소각도 굴곡에서 검사한 상완/전완/허벅지/종아리 길이 오차는 부동소수점 수준이다. 이 검사만으로 관절 관통이나 실제 운동의 자연스러움이 통과된 것은 아니다.

이 실행 환경의 단일 측정에서 새 3/4 자세 컴파일+제출 약62ms, 정지 Path2D 캐시 반복 제출 중앙값 약0.2ms였다. 실제 수치는 `validation.json` 참조. **래스터/합성 완료 시간, 게임 RAF/FPS, 실제 모바일 성능 측정이 아니다.** 약1.4만 가시면을188개 그리기 명령으로 묶는다. 새 자세를 매 프레임 컴파일하는 방식으로는 프레임 예산에 맞지 않는다.

따라서 **Canvas로 같은 좌표의 세 시점과 연결 구조를 그리는 것은 확인했으나, 컨셉 수준의 품질을 유지하는 실시간 공용 캐릭터로서의 구현 가능성은 아직 확인되지 않았다.** 이 시제품을 투수/주루/수비에 복제하는 것은 추천하지 않는다. 향후 공유할 대상은 인물 파라미터와 관절 데이터 규약이며, 현재 면 생성 렌더러 전체는 아니다. 이번에는 더 큰 최적화/애니메이션 개발로 범위를 넓히지 않았다.

실제 iPhone Safari, 게임 투구·판정 연동, 다중 선수, 실기기 메모리는 미검증. 기존 오프닝 시안과 실서비스는 그대로 보존. 승인 전 병합/배포 없음.
