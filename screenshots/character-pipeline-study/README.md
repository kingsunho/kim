# 캐릭터 제작 파이프라인 재검토 — 곽빈 1명

2026-10-28 / 별도 브랜치 `visual/character-pipeline-study` / 실서비스·경기 로직·타격 모션 변경 없음.

## 결론

**현재 Canvas 경기와 정해진 카메라를 유지하는 범위에서는 A(방향별 레이어 아트 + 관절 리그)를 추천한다.** 컨셉의 얼굴·옷 명암을 실제 실행 결과에 유지하고, 새 자세마다 수만 개 면을 생성하지 않는 것이 이번 시제품에서 확인됐다. 그러나 현재 자산/조립은 최종 미술 승인을 받은 상태가 아니며, 투구·주루·수비 전체가 완성된 것도 아니다. 모션 제작으로 진행하지 않았다.

B(경량 스타일라이즈드3D)는 자유 카메라 회전, 큰 몸통 회전, 정확한 가림, 다양한 체형에서 장기적 장점이 있다. **이번에 B용 인물 모델/리그를 만들거나 GPU 엔진을 도입하지 않았으므로, B보다 A가 빠르다는 실측 비교는 아니다.** 현재 코드와 자산 기반에서 필요한 추가 작업/위험과 A 시제품을 근거로 한 조건부 추천이다. 향후 목표가 자유 회전 카메라로 확정되면 B를 다시 검토해야 한다.

## 제출 자료 — 무엇이 실제 실행 결과인가

- `comparison.png`: 왼쪽 생성 컨셉, 가운데 이전 도형 렌더 캡처, 오른쪽 **실제 A 실행 Canvas**. 비교 편의를 위한 브라우저 배치/확대이며 렌더를 보정하지 않았다.
- `layer-views.png`: 정면·3/4·측면 실제 Canvas. 방향별 별도 레이어 사용.
- `layer-bend.png`: 작은 어깨/팔꿈치/골반/무릎 굴곡의 실제 합성. 야구 투구 모션 아님.
- `layer-joints.png`: 위 굴곡의 동일 골격 오버레이.
- `mobile-390.png`: 실제 Chromium390×844 viewport의240 CSS px 캐릭터. 실기기나 실제 게임 UI가 아님.

생성 모델로 만든 3장의 투명 아틀라스는 **실제로 런타임이 사용하는 아트 자산**이다. 그 생성 결과만을 실행 성과로 보고하지 않는다. 위의 `layer-*` 파일은 HTML 페이지가 자산을 분리·조립해 Canvas에 그린 브라우저 캡처다. 원본 컨셉 한 장을 돌리거나 최종 캐릭터 PNG를 포즈마다 바꾸는 방식이 아니다.

## 현재 코드에서 확인한 재사용 범위

1. `visual/batting/approved/renderer.js`의 `sdFullSwing` / `R.world`: 골반·흉곽·머리·양쪽 어깨/팔꿈치/손·고관절/무릎/발, 고정 관절 길이, IK 및 양손/배트 그립 관계. **의미 있는 관절 데이터/제약은 재사용 후보**다.
2. `visual/batting/approved/ready.js`의 `ReadyWorld.scene`, `plant/contact/extension/follow`의 단계 샘플링: 타자→투수 방향, 로컬 축→필드 월드, 보정된 고정 카메라의 `world/project`, 승인된 포즈 타임라인. 새 아트에 연결하더라도 이 포즈 원본과 판정 시각은 보존해야 한다.
3. `visual/batting/adapter.js`: `ApprovedBattingFactory.full(ms)` → `view.actor(g,S)`의 모델/표현 분리, C1 시간, 코스 지원/fallback, 수명 관리. 표현 어댑터의 위치는 참고할 수 있지만 **이번에 교체하지 않았다.**
4. 기존 렌더러의 곡면 UV와 소프트웨어 깊이/readback은 공유하지 않는다. `renderer.js`의 `sdBattingArms` 계열에는 `getImageData`/픽셀 반복이 있다. 이를 선수마다 복제하면 안 된다.
5. `index.html`의 `MV_CAMS`, `MV_PORT`, `mvCamGeom`: 현재는 여러2D 카메라의 확대/앵커/정규화 좌표다. 이를3D 카메라 행렬로 그대로 간주하면 안 된다.

이번 A 시제품은 기존 리그를 직접 호출하는 통합판이 아니다. **같은 종류의 관절 데이터 계약을 사용하는 독립 FK**다. 승인 리그는 로컬Y-up/필드Z-up 변환이 있고 이 시제품은Y-down/Z-front이므로 실제 retarget시 축·단위·인물 비율을 명시적으로 변환해야 한다. 기존 게임의 카메라/판정에 임의로 맞추는 작업은 하지 않았다.

## 이전 약62ms의 원인 분리

원본 `visual/kwak-study/actor.js`를 변경하지 않고 브라우저에 로드하는 문자열에 타이밍만 삽입했다. 최종 측정 cold6회 평균:

| 단계 | 평균ms |
|---|---:|
| 관절 좌표 계산 | 0.10 |
| 관절 외 곡면/삼각형 생성 | 6.87 |
| 투영·노멀·정렬·Path2D 준비 및 경계 | 52.82 |
| Canvas 명령 제출 | 2.25 |
| API 반환 포함 전체 | 62.10 |

동일 포즈 캐시를 반복하면 매우 작아지지만, 준비된 런타임에서 **매번 다른30개 자세**를 넣으면 전체 중앙값48.6ms, P95 약73.2ms였다. 가장 긴 약398.7ms 표본도 원자료에 남겼다. GC/Canvas 작업 지연의 분리는 별도 트레이스 없이는 확정하지 않는다. 요점은62ms가 관절 계산 자체나 최초 파일 로드만의 비용이 아니라는 것이다. 이 도형 생성 경로는 계속 세부 수정하지 않았다.

이전 도형 경로의 비용 분리는 연속 호출 마이크로벤치이고, 새 A의 RAF 시험은 프레임 간격을 둔 별도 시험이다. 따라서 두 결과를 같은 조건의 게임 FPS A/B 비교로 해석하지 않는다. 명령 제출 시간은 GPU/합성 완료 시각이 아니다. 계측 코드 자체의 비용과 헤드리스 환경 영향을 포함하므로 순수한 하드웨어 성능으로 해석하지 않는다.

## A 시제품의 구조

소스: `visual/pipeline-study/index.html`, `layers.js`, `assets/atlas.json`, `front/quarter/side.png`. 외부 라이브러리 추가 없음. 로컬 정적 서버로 저장소 루트를 제공하고 `/visual/pipeline-study/`를 연다. 단순 file://는fetch 제한 때문에 대상이 아니다.

각 방향16파트: 머리/얼굴/머리카락, 모자, 흉곽 셔츠, 골반, 좌우 상완/전완/손, 좌우 허벅지/종아리/신발. 머리 안의 얼굴·머리카락은 아직 한 파트로 묶여 있고, 표정/머리 스타일 레이어 독립 교체는 미구현이다.

- 준비: PNG decode → 메타데이터의 파트 사각형 → 파트별 offscreen Canvas. 옷의 절단면은 소스 자산을 정리하고, 준비 시 알파 겹침 영역을 만든다. 원본 아틀라스 참조는 해제한다.
- 매 프레임: FK → 방향별 파트 선택 → 관절 양 끝에 맞춘 affine 변환 →16개 `drawImage`. 프레임별 픽셀 readback/면 생성/새 포즈 이미지 생성 없음.
- 골반→척추/어깨/머리, 어깨→팔꿈치→손목, 골반→고관절→무릎→발목으로 부모 회전 전달.
- 가까운/먼 팔·다리를 구분한 제한된 painter ordering. **픽셀 단위의 정확한 3D 가림은 아니다.** 팔이 몸통을 가로지르는 큰 동작은 추가 분할/가림 설계가 필요하다.
- 정면/3/4/측면은 미리 그린 방향별 자산이다. 연속 yaw를 보장하지 않으며 방향이 바뀔 때 pop 가능성이 있다. 이번에는 이를 회전 영상으로 감추지 않았다.

`LayerCharacter.load()`로 만든 한 자산 묶음을 여러 번 `draw()`해 공유한다. 인물마다3개 아틀라스를 다시decode하는 구조로 쓰지 않는다. `dispose()`는 파트 Canvas를0크기로 만들고 참조를 제거한다. 아직 실제 게임의 장면 종료/리그 자산 관리에 연결하지 않았다.

## A 최종 측정 — 실제 기기 아님

호스트 headless Chromium. 모바일 항목은390×844·DPR2 **에뮬레이션**이다. 같은 곽빈 자산으로 1/4/10명을 그리고, 각 프레임에 다른 작은 관절 값을 넣었다. 정지 포즈 전체를 캐시해 숫자를 낮추지 않았다. 조건별20 warm-up +180 RAF 프레임. draw16회/명. 본게임의 배경·UI·판정·물리 비용 없음.

| 390×844 DPR2 | 4 | 0.7 | 1.2 | 16.7 |

모바일 에뮬레이션10명에서 최대 RAF33.4ms도 있었다. **무조건60FPS/프레임 지연 없음이라고 결론내리지 않는다.** JS 항목은 합성 제출과 별도의 작은 FK 측정 호출까지 포함한 값이며 GPU 완료 시간이 아니다.

같은 실행의 전체 자산 준비 약92.2ms = 로컬fetch/decode 약84ms + 파트 준비 약8ms. 최초 네트워크/폰decode 속도와 다르다. 처음decode한 원본3장RGBA 논리 크기18.0MiB, 유지하는48파트 논리 크기7.89MiB. 준비 순간에는 둘이 겹쳐 존재할 수 있다. GPU 사본·브라우저 내부 캐시·프레임버퍼를 포함한 실제 RSS/VRAM은 **미측정**이다. 이미지decoder 참조를 지웠다고 즉시 메모리가 반납됐다고 주장하지 않는다.

## 재사용성 설계와 남은 외형 문제

공유할 것은 관절 의미/길이·월드변환·유니폼/얼굴 자산 인터페이스다. A의체형변형은소폭길이/폭조절까지만검증했다. 극단적키/체형을같은그림으로늘리면망가지므로체형템플릿이필요하다. 현재 시제품은 곽빈한명만 구현했고 얼굴/피부색/팀/등번호를자유롭게 바꾸는 완성된 인물생성기가 아니다.
